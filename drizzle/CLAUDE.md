# Migrations and row-level security

SQL migrations generated by `bun run db:generate` from `src/db/schema/` (one module per entity), applied in order by `src/db/migrate.ts` (the PreSync migrate Job on deploy, `make run` locally). Never `db:push` to the cluster. This file is notes for agents; the migrator only reads the files listed in `meta/_journal.json`.

## The tenant is a club

Every row of app data belongs to exactly one club, and **every table has a non-null `club_id`** (`REFERENCES club(id) ON DELETE CASCADE`), even when the row's parent already has one. Child tables (`sale_item`, `coach_activity`, `coach_class_attendee`) carry their own copy because the row-level security policy can only see the row itself.

The only tables without `club_id` are the tenancy and identity ones:

| Table | Why it isn't club-scoped |
| --- | --- |
| `club` | The tenant itself. |
| `club_member` | Links users to clubs. It has `club_id`, but it's read to find out a request's club, before one is known. |
| `user`, `session`, `account`, `verification` | Better Auth's identity tables. A user can belong to several clubs. |

The integration suite (`row-level security` in `src/db/integration.test.ts`) fails if a table outside that list has no non-null `club_id`, or lacks RLS, FORCE or the policy. If you add a table to the list, give the reason here.

## Row-level security

Every club-scoped table has:

```sql
ALTER TABLE "t" ENABLE ROW LEVEL SECURITY;
ALTER TABLE "t" FORCE ROW LEVEL SECURITY;
CREATE POLICY "club_isolation" ON "t" FOR ALL
  USING (club_id = current_setting('app.club_id', true) OR current_setting('app.bypass_rls', true) = 'on')
  WITH CHECK (<the same>);
```

- **FORCE is required.** The app's role (`padel_admin`, and `padel_admin_dev` locally) owns the tables, and owners skip RLS unless it's forced. drizzle-kit doesn't generate FORCE, so add it by hand to the migration that creates the table.
- **The policy comes from the schema.** Declare tables with `clubIsolation()` in their extra config (see `src/db/schema/club-isolation.ts`), so drizzle-kit generates `ENABLE ROW LEVEL SECURITY` and `CREATE POLICY` and keeps them in its snapshot.
- **The settings are per transaction.** `src/db/tenant.ts` sets `app.club_id` with `set_config(..., true)` at the start of every transaction, and wraps each query run outside one in its own transaction. The app goes through PgBouncer in transaction mode, so a session-level `SET` would leak to other clients. Never set either variable with a plain `SET` in app code.
- **No setting means no rows.** Without `app.club_id`, club-scoped tables look empty and inserts fail with "new row violates row-level security policy". A forgotten scope fails closed. It never leaks data.
- **Superusers and `BYPASSRLS` roles skip all of this.** CI runs its database jobs as an ordinary owner for that reason (`scripts/ci-db-owner.ts`).
- Foreign-key checks and `ON DELETE CASCADE` ignore RLS, so deleting a club still removes all of its rows.

What RLS protects against: a query that forgets its `club_id` filter, or a join that reaches another club's rows. It doesn't protect against SQL injection, which could set `app.bypass_rls` itself. Keep filtering by club id in queries too: it's still the authorization check, and it lets Postgres use the indexes.

## Where the club comes from

- **Requests:** `tenantScopeMiddleware` (`src/start.ts`) gives each request an empty scope. `resolveActiveClubId` (`src/lib/auth.server.ts`, which `currentClubId` and `requireClubId` call) fills it in with the active club. Server functions get the scope automatically by going through those helpers.
- **A club named explicitly:** wrap the work in `withClubScope(clubId, fn)`. This covers creating a club (`createClubRecord`), the platform API (`/api/platform/clubs/:clubId/...`) and the AI tools, which run while the response streams, after the request's async context is gone.
- **Scripts and tests acting on every club:** `bypassRlsForProcess()` (seed, reset, the integration suite) or `withRlsBypass(fn)`. Raw `pg` pools that skip `@/db` (`migrate.ts`, the integration suite's own pool) connect with `options: "-c app.bypass_rls=on"`. Only do that on direct connections, never through PgBouncer. Never bypass in app code.

## Writing migrations

- **A new club-scoped table:** add `clubId` (not null, cascade to `club`) and `clubIsolation()` in the schema, run `bun run db:generate`, then add `ALTER TABLE ... FORCE ROW LEVEL SECURITY;` to the generated SQL.
- **Adding `club_id` to an existing table:** drizzle-kit generates `ADD COLUMN ... NOT NULL`, which fails on existing rows. Rewrite it as add nullable, backfill from the parent row, then `SET NOT NULL` (see `0022_club_rls.sql`).
- **Data migrations (UPDATE/INSERT/DELETE on club tables):** `migrate.ts` connects with `app.bypass_rls=on`, so they see every club's rows. Tests and `make dev-reset` run migrations the same way.
- Inserts into club-scoped tables must set `club_id` to the scoped club, or the policy's `WITH CHECK` rejects them.
- A comment alone between `--> statement-breakpoint` markers becomes an empty statement. Put comments on the line above a statement, without a breakpoint between them.
